# 앱 입고 (`intake`)

만든 앱을 올리면 회사 표준 규칙에 맞는지 기계가 먼저 보고,
담당자 검토를 거쳐 배포로 넘어간다.

## 왜 있나

앱을 받으면 담당자가 점검 스크립트를 돌려 보고, ✗ 가 있으면 알려 주고,
고쳐서 다시 받고를 반복했다. 오가는 횟수만큼 시간이 든다.

**만든 사람이 스스로 돌려 볼 수 있게 하면 그 왕복이 사라진다.**
담당자에게 오는 시점에 이미 절반은 걸러져 있다.

## 흐름은 넷이다

```
올린다 → 기계가 본다 → (통과하면) 검토 요청 → 담당자가 승인·반려
```

✗ 가 하나라도 있으면 **요청 버튼이 열리지 않는다.** 기계가 잡을 수 있는 것을
사람에게 넘기지 않는다. 대신 무엇을 어떻게 고치면 되는지를
**그대로 붙여넣을 수 있는 글**로 만들어 준다(`app/fixes.py`).
만든 사람은 대개 비개발자고, 반려 사유를 읽어도 쓰던 AI 에 무엇을 말해야
할지를 모른다. 거기까지 가 줘야 왕복이 끝난다.

검사 결과 27가지 문구마다 「왜 막는지 · 어디를 어떻게 고치는지 · 붙여넣을 코드」가
붙어 있다. 도커 설정처럼 큰 항목이 걸리면 그 아래 작은 항목들은 접는다 —
같은 파일을 두 번 고치라고 하면 사람이 헷갈린다.

## 담당자 화면

`/intake/admin` — 포털이 담당자로 지정한 사람에게만 열린다(`X-User-Role: admin`).

| 탭 | |
|---|---|
| 검토 요청 | 지금 기다리는 것 |
| 전체 · 승인됨 · 반려됨 | 지나간 것 |
| 장부 | 서비스별로 무슨 일이 몇 번 있었나 |

제출물을 누르면 원본을 받고, 고칠 내용 프롬프트를 뽑고, 승인·반려한다.
상세 맨 위에 **포털에 이미 있는 서비스인지**를 적어 둔다 — 승인 뒤에 할 일이
갈리기 때문이다. 이미 있으면 깃에 올려 다시 배포하면 끝이고, 새 서비스면
nginx 설정·포털 등록·접근 권한까지 같이 잡아야 한다.

## 장부는 한 표에 쌓는다

입고도, 나중에 붙일 코딩 에이전트 작업도, 배포도 전부 `events` 한 표에
같은 모양으로 들어간다. 종류만 `kind` 로 구분한다.

```sql
SELECT service_id, SUM(cost_krw) FROM events GROUP BY service_id;
```

"이 서비스에 지금까지 얼마가 들었나" 를 한 줄로 뽑으려고 이렇게 두었다.
지금은 입고만 들어 있다.

## 같은 주소를 두 앱이 가져가지 않게

서비스 ID 를 적는 동안 포털에 물어본다(`GET /api/services/ids`).
이미 있는 주소면 **그 자리에서 알려 준다.** 다만 막지는 않는다 —
이미 있는 앱을 고쳐서 다시 올릴 때는 같은 ID 가 정답이다.
기계는 "이건 이미 있습니다" 까지만 말하고, 맞는지는 사람이 판단한다.

포털에 못 물어봤을 때는 **「비어 있습니다」라고 하지 않는다.**
확인도 안 하고 비었다고 해 놓고 나중에 nginx 에서 부딪히는 것이 제일 나쁘다.

## 포털 첫 화면의 배지

담당자 앞에 밀려 있는 것이 있으면 포털 앱 카드에 빨간 숫자가 붙는다.
포털은 앱이 무슨 일을 하는지 모르므로 개수를 세지 않고 **앱에게 물어본다** —
앱이 `GET api/badge` 로 `{"count": 2, "label": "검토 요청 2건"}` 을 내놓으면 된다.
안 만든 앱은 404 가 오고 포털이 조용히 넘어간다. 그래서 이 기능 때문에
기존 앱을 고칠 일이 없다.

## 체험판에서는 올리기를 받지 않는다

이 앱은 이 포털에서 유일하게 **남이 준 파일을 서버에서 푸는** 앱이다.
공개된 곳에 그 길을 열어 둘 이유가 없어서, 미리 넣어 둔 예시 셋 중에서 고르게 한다.

```
회의실예약    규칙대로 만든 앱          ✓ 32  △ 0  ✗ 0
출입증관리    로그인을 스스로 만든 앱   ✓ 22  △ 8  ✗ 2
비품신청      여기저기 틀린 앱          ✓ 16  △ 10 ✗ 6
```

**검사하는 코드는 올릴 때와 같은 것을 쓴다.** 예시만 다른 길로 들어가면
「예시에서는 되는데」가 된다. 푸는 단계만 없다.

막는 것이 두 겹이다 — 앱이 스스로 403 을 내고(`DEMO_MODE=1`),
데모 가드도 올리기 주소를 안 열어 둔다. 한 겹으로 버티게 두지 않는다.

사내에서는 `DEMO_MODE=0` 으로 두고 그대로 올려서 쓴다. 그때 켜지는 안전장치 —
zip 아닌 파일 · 폴더 밖을 가리키는 경로(zip slip) · 압축 폭탄 ·
파일 수(5000) · 푼 뒤 크기(300MB) · 검사 시간(120초).

## AI 가 고친다 — 걸린 앱도, 이미 돌고 있는 서비스도

검사만 있으면 왕복이 끝나지 않는다. 걸린 사람은 「그래서 뭘 고치지」에서 멈추고,
고칠 사람이 개발자가 아니면 거기서 끝난다. 그래서 고치는 쪽까지 붙였다.

```
① 올린 앱이 걸렸다        →  [AI 가 고치기]  → 다시 검사 → 새 제출물
② 이미 돌고 있는 서비스   →  요청 한 줄     → 다시 검사 → 새 제출물 + 반영 파일(.patch)
③ 내가 직접 고치고 싶다   →  [지금 코드 내려받기] → 쓰던 AI 로 고침 → 다시 올리기
```

셋 다 **나오는 것이 같다** — 제출물 하나와 반영 파일 하나. 담당자가 보는 자리도 하나다.

### 하지 않는 것

- 깃에 올리지 않는다. 배포하지 않는다. 저장소는 **읽기 전용**으로 붙인다.
  도커를 부리려면 서버 전체 권한을 이 컨테이너에 줘야 한다 — 그 값이 너무 크다.
  승인 뒤 반영은 사람이 한다: 반영 파일 받기 → `git apply` → 커밋 → `./deploy.sh <폴더>`.
- 비밀값(`.env`)과 운영 자료(`data/`)는 AI 에게 보내지도, zip 에 담지도 않는다.
- 포털·프록시·이 앱 자신은 고치지 않는다(`AI_EDIT_EXCLUDE`).
  잘못 고치면 이 기능을 쓰는 화면까지 같이 멈춘다.
- AI 가 돌려준 것은 **자료로만** 다룬다. 파일 내용과 찾아 바꿀 덩어리일 뿐,
  실행하는 길이 없다. 폴더 밖·`.env`·`data/` 를 가리키면 그 덩어리만 버린다.

### 파일이 커서 통째로 못 받는다

화면 파일 하나가 80~150KB 인 앱이 흔하다. 통째로 다시 받으면 출력 한도와
시간 제한에 걸린다. 그래서 두 걸음으로 나눈다 —
**① 볼 파일 고르기 → ② 바꿀 부분만 찾아 바꾸기**(`app/ai_edit.py`).
못 찾은 덩어리는 한 번 더 물어본다. 그래도 못 찾으면 그 사실을 화면에 적는다.
줄바꿈(CRLF/LF)은 원래대로 지킨다 — 안 그러면 patch 가 파일 전체를 바꾼 것처럼 보인다.

## 무엇이 바뀌었나 — 세 겹으로 보여 준다

담당자에게 patch 를 던지고 「읽어 보세요」 하면 아무도 안 읽는다. 그래서 세 겹이다.

| 겹 | 무엇 | 누가 만드나 |
|---|---|---|
| 눈여겨볼 것 | 없어진 주소 · DB 구조 변경 · 바깥 인터넷 주소 · 권한 코드 · 새 설정값 · zip 에 없는 파일 | 기계 (`app/changes.py`) |
| 센 것 | 고친 파일 수, 늘어난 줄, 지운 줄, 파일별 내역 | 기계 |
| 사람 말 | 추가된 것 · 바뀐 것 · **빠진 것** · 봐야 할 것 | AI (한 번만, 파일로 남긴다) |

「빠진 것」을 일부러 넣었다. AI 는 고쳤다고 말하면서 요청의 절반만 한 적이 있다.
사람이 그걸 알 방법이 화면에 있어야 한다.

반영 파일은 `git apply` 로 그대로 들어가는 patch 다 — 담당자가 zip 을 통째로
덮어쓰지 않아도 된다. 통째로 덮어쓰면 그 사이 남이 고친 것이 조용히 사라진다.

## 체험판에서 다른 것은 셋뿐이다

- **AI 는 진짜로 부른다.** 흉내만 내면 이 도구의 핵심(고쳐서 다시 검사까지 간다)이
  안 보인다. 대신 하루 횟수를 막고, 한 번 부르고 잠깐 쉰다(`DEMO_AI_DAILY`,
  `DEMO_AI_MIN_GAP`). 세는 곳은 **장부(events)** 다 — 「몇 번 썼나」를 따로 세면
  돈이 든 기록과 반드시 어긋난다.
- **미리 띄워 보기는 설명만** 한다. 사내판에는 고친 것을 운영과 따로 띄워
  담당자만 눌러 보는 실행기가 있다(바깥 인터넷 차단 · 비밀값 없음 · 권한 뺀
  컨테이너 · 2시간 뒤 자동 삭제). 공개된 서버에서 아무나 컨테이너를 띄우는
  길은 열어 두지 않는다.
- **담당자 지정이 없다.** 사내판은 「그 앱의 담당자 + 포털 관리자」에게만
  고칠 서비스를 보여 준다. 여기서는 들어온 사람 모두에게 보인다 —
  보여 주려고 만든 화면이다.

검사·AI·변경 비교 코드는 사내판과 **같은 파일**이다. 다른 것은 검사기를 감싸는
얇은 껍데기 하나뿐이다(`app/checker_sync.py`) — 체험판 검사기는 bytes 를 받아
비동기로 돌고, 사내판은 zip 경로를 받아 동기로 돈다. 모양만 맞춰 준다.

## 규칙은 한 파일뿐이다

`rules/check-intake.sh` 하나를 화면도 명령줄도 같이 본다.

```bash
bash rules/check-intake.sh ../leave-anomaly     # 명령줄에서도 같은 결과
```

규칙을 두 벌로 두면 「화면은 통과라는데 내 PC 에선 ✗」가 난다.
그래서 앱 안에 복사본을 만들지 않고 이 한 파일만 둔다.

## 남기지 않는다

- **올라온 코드를 실행하지 않는다.** 푸는 것과 읽는 것만 한다.
  검사 도구가 검사 대상을 실행하면, 검사가 곧 침입 통로가 된다
- 올라온 zip 은 임시 폴더에서 검사하고 지운다
- 제출 이력과 장부는 **컨테이너 안에만** 쌓인다. `./data` 볼륨이 없다.
  다시 띄우면 사라지고 예시 이력이 새로 깔린다 — 남의 손이 닿은 것이
  다음 사람에게 남지 않는다. 사내에서는 볼륨을 붙이면 그대로 쌓인다

## 체험판인데 승인까지 눌러 볼 수 있는 이유

파일은 못 올리지만 **흐름 전체**는 볼 수 있어야 한다. 그래서 뜰 때
예시 셋을 실제 검사기에 통과시켜 제출 이력으로 깔아 둔다.
사람 이름과 부서만 지어냈고 **✓△✗ 숫자와 리포트는 진짜다** —
숫자까지 지어내면 「고칠 내용 프롬프트」가 리포트와 안 맞아 빈 껍데기가 된다.

앞사람이 전부 반려해 두면 다음 사람이 볼 것이 없으므로,
한동안 조용하면(`DEMO_RESET_MIN`, 기본 30분) 다시 깐다.

## 기계가 못 보는 것

화면 맨 아래에 사람이 볼 목록 다섯 가지를 같이 띄운다.
숫자가 맞는지, 제일 큰 실제 파일로 돌려봤는지, 지우기가 있는지 —
**에러는 티가 나지만 틀린 숫자는 조용하다.**
