# 작업 순서 — 고치고, 확인하고, 올리고, 서버에 반영하기

포트폴리오는 **세 군데**에 있다. 어디서 무엇을 하는지가 늘 헷갈려서 한 장에 적어 둔다.

```
회사 PC / 집 PC          GitHub                Azure 서버
(고치는 곳)         →   (옮기는 통로)    →   (남에게 보이는 곳)
C:\claude\portfolio                          portal.trendkit.app
```

규칙은 하나다. **고치는 것은 언제나 내 PC 에서.** 서버는 받기만 한다.

---

## 들어가는 문 네 개

| 어디 | 주소 | 체험판 잠금 | 쓰는 때 |
|---|---|---|---|
| 내 PC | `http://localhost:8090/` | **있음** | 평소. 방문자가 보는 것과 똑같다 |
| 내 PC | `http://127.0.0.1:8082/` | **없음** | 데모 내용을 화면에서 고칠 때 |
| 서버 | `https://portal.trendkit.app` | **있음** | 남들이 보는 곳 |
| 서버 | `127.0.0.1:8082` | **없음** | 서버 것을 화면에서 고칠 때 (SSH 터널 필요) |

서버의 8082 에 들어가려면 먼저 터널을 뚫는다. 그 SSH 창을 닫으면 문도 닫힌다.

```bash
ssh -L 8082:127.0.0.1:8082 <계정>@<서버주소>
#  → 브라우저에서 http://127.0.0.1:8082/
```

## 새 PC 에서 처음 할 일

회사 PC · 집 PC 를 오가므로, PC 를 바꿨을 때 이것만 하면 된다.

```powershell
git clone https://github.com/9seebird/portal-portfolio.git portfolio
cd portfolio
.\demo.ps1               # setup 까지 알아서 부른다 (.env · 훅 · 자료 · 띄우기)
```

이미 클론이 있으면 `git pull` 부터 하고 `.\demo.ps1` 이다.

그리고 `portal\.env` 의 `OPENAI_API_KEY` 를 채운 뒤 `.\deploy.ps1 portal`.
이것만은 기계가 지어낼 수 없다. 안 넣어도 **챗 빼고 나머지는 다 돌아간다.**

> **배포는 이 PC 와 무관하다.** 깃허브가 서버에 직접 붙으므로, 어느 PC 에서
> push 하든 서버에는 똑같이 반영된다. 이 PC 에 준비하는 것은 **개발 환경**이다.

그리고 **`.secretwords` 를 다른 PC 에서 복사해 온다.** 저장소 뿌리에 두면 된다.

이 파일은 「저장소에 있으면 안 되는 낱말」 목록이다 — 실제 직원 이름 ·
실제 도메인 · 실제 IP 대역. **실명이 들어 있으므로 깃에 올리지 않는다**
(`.gitignore`). 그래서 PC 마다 한 번씩 손으로 두어야 한다.

없으면 `git push` 가 이렇게 막힌다. 조용히 넘어가지 않는다.

```
✗ 낱말 목록이 없습니다 (.../.secretwords)
  이 PC 에서는 실명 검사를 할 수 없어 push 를 막습니다.
```

> **왜 깃허브 Secrets 에 안 넣나**
> 넣으면 CI 도 실명을 검사해 주지만, 실명 목록이 있는 곳이 한 군데 늘어난다.
> 대신 검사를 push **앞에** 세웠다 — 걸리면 깃허브에 아무것도 도달하지 않는다.
> 한 번 올라간 것을 히스토리에서 지우는 쪽이 훨씬 번거롭다.

## 전체 흐름 (이것만 보면 된다)

### 1단계 — 내 PC 에서 고친다

소스를 고쳤거나, 8082 로 들어가 화면에서 고쳤거나 둘 중 하나다.

### 2단계 — 내 PC 에서 띄워 본다

```powershell
cd C:\claude\portfolio
.\deploy.ps1 <앱이름>          # 예: .\deploy.ps1 edu
.\deploy.ps1                   # 인자 없으면 전부
```

**★ `.py` · `.js` · `.html` 을 고쳤으면 이 단계를 건너뛸 수 없다.**
앱들은 소스를 **이미지 안에 구워 넣는** 방식이라(`Dockerfile` 의 `COPY app ./app`),
파일만 고치고 컨테이너를 그대로 두면 **아무 일도 일어나지 않는다.**
`deploy.ps1` 이 `docker compose up -d --build` 를 부르면서 이미지를 다시 만든다.

무엇을 고쳤을 때 무엇을 다시 띄워야 하는가:

| 고친 곳 | 다시 띄울 것 |
|---|---|
| `edu/app/**` | `.\deploy.ps1 edu` |
| `portal/app/**` | `.\deploy.ps1 portal` |
| `it-asset/**` | `.\deploy.ps1 it-asset` |
| `proxy/conf.d/**` · `proxy/apps/**` | `.\deploy.ps1 proxy` |
| `proxy/docker-compose.yml` (포트) | `.\deploy.ps1 proxy` |
| 8082 로 들어가 화면에서 고친 것 | **없음** (DB 라서 바로 반영) |

### 3단계 — 지어낸 자료를 바꿨으면 다시 심는다

`*/seed_demo.py`, `tools/*.py`, `tools/company.py` 처럼 **처음 화면을 만드는 것**을
고쳤을 때만 해당한다.

```powershell
.\demo.ps1 -Reseed
```

```bash
./demo.sh --reseed        # 서버
```

이 한 줄이 두 가지를 한다.

1. `tools/make_demo_data.py` 로 씨앗 파일(엑셀·PPT·JSON)을 다시 만든다
2. 떠 있는 앱마다 들어가서 **지우고 다시 넣는다** (자산관리 · 연차 · 매뉴얼 · 교육)

띄우지도 않고 `.env` 도 건드리지 않는다. **이미 떠 있는 앱에 자료만** 넣는다.
지금 들어 있는 체험판 데이터는 지워진다 — 그것이 목적이다.

**순서가 중요하다 — 2단계(빌드)를 먼저, 3단계(자료)를 나중에.**
반대로 하면 컨테이너 안의 **옛 코드**가 돌아서 고친 것이 반영되지 않는다.

> 평소 실행(`.\demo.ps1`)은 자료가 이미 있으면 **건드리지 않는다.**
> 방문자가 만들어 둔 화면을 배포 한 번에 날리지 않으려는 것이다.
> 그래서 「고쳤는데 옛 자료가 그대로」일 때는 `-Reseed` 가 필요하다.

### 4단계 — 확인한다

```powershell
# 화면으로
start http://localhost:8090/

# 자동 점검 (체험판 잠금이 제대로 걸려 있는지)
python tools\check_demo.py
```

### 5단계 — 깃에 올린다

```powershell
git status                     # 무엇이 바뀌었는지 먼저 본다
git add <파일들>               # 이름을 대는 편이 안전하다
git commit -m "무엇을 왜 고쳤는지"
git push
```

`data/` 폴더는 `.gitignore` 에 있어서 **DB 는 절대 올라가지 않는다.**
그래서 8082 로 들어가 화면에서 지운 것은 **git 으로 서버에 옮길 수 없다.**
서버에도 반영하려면 씨앗 코드를 고치거나(권장), 서버 8082 에서 똑같이 지워야 한다.

### 6단계 — 서버에 반영한다 — **자동이다**

`git push` 하면 깃허브가 알아서 한다. 손댈 것이 없다.

```
push → 검사(셸·파이썬·JS 문법 · 회사이름 · 유출 · 테스트 165개)
     → 통과하면 서버에 SSH → autodeploy.sh
     → 받고 · 다시 만들고 · 띄우고 · /health 확인
     → 대답이 없으면 직전 커밋으로 스스로 되돌림
```

깃허브 저장소 → **Actions** 탭에서 진행을 본다. 이 줄이 나오면 끝난 것이다.

```
✓ 배포 완료 · http://127.0.0.1:8081/health 응답함
```

**여기서도 자동이 아닌 것은 3단계(자료 다시 심기)뿐이다.** 데이터를 지우고
다시 넣는 일이라 배포 때마다 돌면 방문자가 만들어 둔 화면이 사라진다.
지어낸 자료를 바꿨을 때만 서버에서 한 줄 친다.

```bash
ssh <계정>@<서버>
cd /srv/portal && ./demo.sh --reseed
```

**배포가 실패했을 때만** 서버에 들어간다. Actions 로그에 이유가 그대로 찍혀 있다.

```bash
cd /srv/portal
tail -40 autodeploy.log        # 서버 쪽 기록
./preflight.sh                 # 받을 준비가 됐는지
```

> 배포는 **어디서 push 하든 똑같이 돈다.** 깃허브가 서버에 직접 붙는 구조라
> 회사 PC · 집 PC · 웹 어디서 올리든 상관없다.

## 자주 틀리는 것

**"고쳤는데 화면이 그대로다"**
→ 2단계를 안 했다. `.\deploy.ps1 <앱>` 으로 이미지를 다시 만들어야 한다.

**"씨앗을 고쳤는데 옛 내용이 다시 살아난다"**
→ 2단계 없이 3단계만 했다. 컨테이너 안의 옛 코드가 돈 것이다. 빌드 먼저.

**"화면에서 지웠는데 서버엔 그대로다"**
→ DB 는 git 에 안 올라간다. 씨앗 코드를 고쳐야 서버까지 간다.

**"서버에서 `git pull` 이 local changes 어쩌구 하며 막힌다"**
→ 서버에서 파일을 직접 고쳤다는 뜻이다. 서버는 받기만 하는 곳이다.
   `git -C . checkout -- <그 파일>` 로 되돌리고 다시 `./deploy.sh`.

**"화면이 텅 비었다 / 로그인만 뜬다"**
→ 자료가 없는 것이다. 파일을 복사하지 말고 `./demo.sh` 를 다시 돌린다.
   (서버는 `./demo.sh --behind` — 이걸 빼면 포트 설정이 덮어써져 502 가 난다.)

**"nginx 설정을 고쳤는데 반영이 안 된다"**
→ 설정에 문법 오류가 있으면 nginx 가 **옛 설정을 그대로 물고** 정상인 척한다.
   `docker exec demo-proxy nginx -t` 로 확인한다.
