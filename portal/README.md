# 사내 AI 챗 포털 — 시작 코드

Hermes 없이 AI API 키만으로 동작하는 최소 구성.
도구 실행 루프, 사용자별 권한, 링크 안내까지 포함되어 있다.

---

## 0. 로컬 PC 에서 먼저 시험하기

서버·도커·도메인 없이 개인 PC 에서 그대로 돌아간다.
필요한 것은 **Python 3.11 이상**과 **AI API 키** 둘뿐이다.

### 윈도우

```bat
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
```

> **윈도우 주의** — `tzdata` 패키지가 반드시 필요하다.
> 윈도우에는 시간대 데이터베이스가 없어서 없으면 `ZoneInfo` 오류가 난다.
> `requirements.txt` 에 포함되어 있으므로 그대로 설치하면 된다.

### API 키 없이 먼저 확인

엑셀 연결이 제대로 됐는지는 AI 호출 없이 확인할 수 있다. 사용료도 들지 않는다.

```bash
python test_tools.py
```

도구 목록, 권한 차단, 엑셀 조회, 링크 생성이 한 번에 출력된다.
**여기서 숫자가 맞으면 엑셀 연결은 끝난 것이다.**

### 그 다음 — 공급자 연결 점검

```bash
python check_llm.py
```

모델 목록과 도구 호출 가능 여부까지 확인해 준다. 여기서 통과해야 서버가 의미가 있다.

### 서버 실행

```bash
uvicorn app.main:app --reload --port 8000
```

`.env` 의 `ANTHROPIC_API_KEY` 를 채운 뒤 `http://localhost:8000/` 접속.

### 로컬 시험 시 참고

| 항목 | 로컬에서는 |
|---|---|
| 인터넷 | AI API 호출용으로만 필요. 사내망 접속 불요 |
| 엑셀 | 내 PC 에 있는 파일 경로를 `.env` 에 지정 |
| 바로가기 링크 | 실제 주소가 없어도 버튼은 정상 표시됨. 눌러야 이동 실패 |
| HTTPS | 불필요 |
| 도커 | 불필요 |

로컬에서 확인이 끝나면 **코드 수정 없이** 그대로 서버에 올리면 된다.
바뀌는 것은 `.env` 내용뿐이다.

## 1. 설치

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # Windows: copy .env.example .env
```

`.env` 를 열어 최소 두 개를 수정한다.

| 항목 | 내용 |
|---|---|
| `ANTHROPIC_API_KEY` | 발급받은 AI API 키 |
| `TOKEN_SALT` | 임의의 긴 문자열로 반드시 변경 |

> `.env` 는 절대 Git 에 올리지 않는다. `.gitignore` 에 이미 등록되어 있다.

## 2. 실행

```bash
uvicorn app.main:app --reload --port 8000
```

브라우저에서 `http://localhost:8000/` 접속.

## 3. 확인 순서

아래 순서대로 확인한다. 앞 단계가 안 되면 뒤는 볼 필요가 없다.

### 3-1. 서버 동작
```bash
curl http://localhost:8000/health
# {"ok":true}
```

### 3-2. 인증
```bash
curl http://localhost:8000/api/tools \
  -H "Authorization: Bearer demo-token-please-change"
```
토큰 없이 호출하면 401 이 나와야 정상이다.

### 3-3. 도구 호출 — 권한 없는 것부터
채팅창에 입력한다.

```
지금 몇 시야
```
`get_server_time` 이 호출되고 시각이 답으로 나오면 **루프가 정상 동작하는 것**이다.
여기까지가 가장 중요한 확인이다.

### 3-4. ai-report 연결
`data/ai_usage.xlsx` 에 샘플 파일이 들어 있다. 실제 파일로 교체하고
`app/tools/ai_report.py` 상단의 열 이름을 실제 엑셀에 맞춘다.

> 시트 지정(`AI_REPORT_SHEET`)은 숫자면 순번(0 = 첫 시트), 문자면 시트 이름으로 처리된다.

```python
COL_DATE = "사용일"
COL_USER = "사용자"
COL_SERVICE = "서비스"
COL_COST = "금액"
```

채팅창에 입력한다.
```
이번 달 AI 비용 얼마야
```

### 3-5. 링크 안내 동작
```
7월 사용 내역 목록 보여줘
```
건수가 `LIST_LIMIT`(기본 5건)을 넘으면 목록을 나열하지 않고
**"상세 화면에서 확인하세요" + 바로가기 버튼**이 나온다.

### 3-6. 권한 차단
`static/chat.html` 의 `TOKEN` 을 `demo-token-no-role` 로 바꾸고 새로고침한 뒤
```
이번 달 AI 비용 얼마야
```
→ 권한이 없다는 답이 나와야 한다. 좌측 앱 목록에서도 해당 기능이 사라진다.

**이 항목이 통과되면 구조가 제대로 잡힌 것이다.**

## 4. 파일 구성

| 파일 | 역할 |
|---|---|
| `app/agent.py` | **핵심.** 도구 실행 루프 |
| `app/registry.py` | 도구 등록·실행. 실행 시점에 접근 권한을 다시 검사 |
| `app/access.py` | **접근 판정의 유일한 기준.** 화면·도구가 모두 이 함수를 거친다 |
| `app/services.py` | 서비스(앱) 저장소. 관리자 화면에서 등록·수정 |
| `app/depts.py` | 부서 목록. 부서명 변경 시 관련 테이블을 함께 갱신 |
| `app/users.py` | 계정 저장소. 부서·관리자 여부·비밀번호 해시 |
| `app/schemas.py` | 도구 응답 형식 (summary / detail_url / truncated) |
| `app/auth.py` | JWT 발급·검증, 접속 IP 판별 |
| `app/memory.py` | 대화 기록·기억·요청 로그·관리 이력 |
| `app/tools/basic.py` | 테스트용 도구 (시간, 내 정보) |
| `app/tools/ai_report.py` | ai-report 엑셀 조회 도구 |
| `app/tools/portal.py` | 앱 안내 도구 (`find_app`) |
| `app/main.py` | FastAPI 엔드포인트 |
| `static/chat.html` | 채팅 화면 (포털 메인) |
| `static/admin.html` | 관리자 화면 (서비스·사용자·이력) |
| `manage.py` | 최초 관리자·부서 생성, 기록 정리 CLI |
| `migrate_roles.py` | 역할 → 부서·관리자 전환 (1회용) |

데이터는 `./data/` 아래 SQLite 파일 세 개에 들어간다.
`portal.db`(서비스), `users.db`(계정), `memory.db`(대화·이력).
도커로 띄울 때는 이 폴더를 볼륨으로 잡아야 재배포 시 날아가지 않는다.

## 5. 도구 추가하는 법

`app/tools/` 에 파일을 만들고 `@tool` 을 붙인다.

```python
from ..registry import User, tool
from ..schemas import ToolResult, ok

@tool(
    name="get_meeting_rooms",
    description=(
        "회의실 예약 현황을 조회한다. "
        "'회의실 비었어?', '회의실 예약 현황', '빈 회의실' 등을 물을 때 사용한다."
    ),
    input_schema={
        "type": "object",
        "properties": {
            "date": {"type": "string", "description": "조회할 날짜. YYYY-MM-DD"}
        },
    },
    service="meeting",           # 이 도구가 속한 서비스 id
                                 # 그 서비스의 접근 범위가 곧 이 도구의 권한이 된다
                                 # 전 직원이 써도 되면 생략
)
def get_meeting_rooms(user: User, date: str | None = None) -> ToolResult:
    ...
    return ok(summary="...", data={...}, detail_url="...")
```

마지막으로 `app/main.py` 의 import 에 추가한다.

```python
from .tools import basic, ai_report, meeting_rooms   # noqa: F401
```

`service=` 를 지정했다면 **관리자 화면에서 같은 id 의 서비스를 먼저 등록**해야 한다.
등록되지 않은 id 를 가리키면 그 도구는 아무에게도 노출되지 않는다.
서비스를 삭제해도 마찬가지로 잠긴다. 권한 없는 도구가 살아 있는 것보다 안전한 쪽이다.

### description 작성 요령

정확도를 가장 크게 좌우하는 부분이다.

- 사용자가 실제로 쓸 표현을 나열한다 — 동의어 포함
- 언제 쓰면 안 되는지도 적는다
- 비슷한 도구가 여러 개면 구분 기준을 명시한다

```
나쁨 : "휴가 조회"
좋음 : "직원의 잔여 연차 일수를 조회한다. 사용자가 휴가·연차·남은 날짜를
        물을 때 사용한다. 사용 내역 목록이 필요할 때는 list_leave 를 쓴다."
```

## 6. 운영 전 반드시 할 것

- [ ] `.env` 의 `JWT_SECRET` 을 임의의 긴 문자열로 교체 (기본값 사용 금지)
- [ ] HTTPS 적용 — 비밀번호와 JWT 가 평문으로 오간다
- [ ] `./data/` 를 도커 볼륨으로 지정하고 백업 대상에 포함
- [ ] 각 서비스의 접근 범위 점검 — 특히 타인 정보를 다루는 서비스
- [ ] `CHAT_LOG_TEXT` 가 `off` 인지 확인 (기본값). 켜 두고 잊지 말 것
- [ ] 예시 서비스가 남아 있으면 삭제
- [ ] AI API 사용량 상한 설정
- [ ] nginx 에 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` 설정
      (IP 제한을 쓸 경우. 없으면 접속 IP 가 전부 127.0.0.1 로 보인다)
- [ ] 즉시 차단이 필요하면 `app/auth.py` 의 '즉시 차단' 주석 해제

- 도구 실행은 전부 우리 서버 안에서 일어난다. MCP 서버나 사내 앱을

  다음 요청에 넘기는 방식으로 확장한다.

## 8. 기억 기능

Hermes 의 "영구 기억"과 같은 원리를 최소 구성으로 구현해 두었다.
**모델이 학습하는 것이 아니다.** SQLite 에 기록을 쌓아뒀다가
다음 요청 때 시스템 프롬프트에 다시 넣어주는 것뿐이다.

### 저장되는 것

| 대상 | 테이블 | 용도 |
|---|---|---|
| 사용자 메모 | `notes` | "나는 IT팀이야" 같은 지속되는 선호 |
| 대화 내역 | `turns` | 직전 대화 맥락 (기본 10발화) |
| 요청 로그 | `logs` | 질문·호출 도구·답변. 오답 개선의 근거 |

### 사용 예

```
나는 IT팀 소속이야 기억해둬        → remember_preference
뭐 기억하고 있어?                  → list_preferences
1번 잊어줘                         → forget_preference
```

저장된 내용은 다음 대화부터 시스템 프롬프트에 이렇게 들어간다.

```
[이 사용자에 대해 기억하고 있는 내용]
- 나는 IT팀 소속이고 자산 관련 문의가 많다
- 금액은 항상 원 단위로 표시
위 내용을 참고하되, 사실 확인이 필요한 사항은 반드시 도구로 조회하십시오.
```

### 설계상 지킨 것

- **명시적 요청이 있을 때만 저장한다.** AI 가 임의로 쌓기 시작하면
  잘못된 내용이 검증 없이 계속 재사용되고, 왜 그렇게 답했는지 추적하기 어려워진다.
- **변하는 사실은 기억하지 않는다.** 잔여 수량·금액은 매번 도구로 조회한다.
  기억에 남은 옛 숫자를 답하는 것이 가장 위험하다.
- **사용자당 상한(기본 20건)을 둔다.** 무한정 쌓이면 프롬프트가 비대해지고
  비용이 늘며 정확도가 떨어진다.

### 확인

```bash
curl http://localhost:8000/api/memory -H "Authorization: Bearer <토큰>"
curl http://localhost:8000/api/logs   -H "Authorization: Bearer <토큰>"   # 관리자만
```

## 9. 서비스 목록과 접근 범위

앱 목록은 코드가 아니라 **관리자 화면(`/admin`)** 에서 등록한다.
앱을 하나 늘릴 때마다 코드를 고쳐 재배포하는 방식은 오래 못 간다.

처음 띄우면 서비스 목록은 **비어 있다.** 실제로 없는 앱이 목록에 떠 있으면
직원이 눌렀다가 없는 페이지를 보게 되고, 그게 "처음 화면이 비어 있다"보다
훨씬 나쁘다. 형태를 먼저 보고 싶으면 빈 화면의 `예시 4개 넣어보기` 를
누르고, 쓰지 않을 것은 지우면 된다.

### 접근 범위 모델

역할(role) 이름을 쓰지 않는다. 앱이 늘면 역할도 같이 늘어나고,
결국 어떤 역할이 무엇을 여는지 아무도 기억하지 못하게 된다.
대신 **서비스마다 누가 쓸 수 있는지**를 직접 지정한다.

| 항목 | 뜻 |
|---|---|
| 전 직원 | 계정이 있으면 누구나 |
| 부서 지정 | 그 부서 소속이면 사용 |
| 개인 추가 | 다른 부서 사람을 한 명씩 추가 |
| 개인 제외 | 부서는 허용이지만 이 사람만 제외 |
| 허용 IP | 비우면 제한 없음 |

판정 순서는 `app/access.py` 에 그대로 적혀 있다.
**제외가 허용보다 우선한다.**

### 포털 관리자는 접근 범위를 통과한다

`is_admin` 계정은 부서·개인 지정과 상관없이 모든 앱을 쓸 수 있다.
방금 배포한 앱을 바로 열어 확인해야 하고, 담당자가 퇴사했을 때
아무도 손댈 수 없게 되는 상황을 막아야 하기 때문이다.

다만 **관리자도 통과하지 못하는 두 가지**가 있다.

| | 관리자 | 이유 |
|---|---|---|
| 접근 범위 (부서·개인) | 통과 | 위 이유 |
| 개인 제외 명단 | 통과 | 같음 |
| **사용 중지** | **막힘** | 중지는 중지다. 예외를 두면 뜻이 흔들린다 |
| **허용 IP** | **막힘** | "누구인가"가 아니라 "어디서 접속하는가"의 문제 |

새로 등록된 앱을 확인하는 순서는 이렇게 된다.

```
앱이 자동 등록됨 (중지 · 접근 범위 없음)
   → 켠다                        이 시점에 들어갈 수 있는 사람은 관리자뿐
   → 관리자가 열어서 확인
   → 접근 범위를 지정한다        직원에게 열린다
```

관리자는 모든 앱의 업무 데이터를 볼 수 있게 되므로, 관리자 계정은
꼭 필요한 사람에게만 준다.

### 쓸 수 있다 ≠ 관리할 수 있다

접근 범위와 별개로 **담당자**를 둔다.

| | 누가 |
|---|---|
| 조회 · 다운로드 · 업로드 | 접근 범위에 든 사람 |
| **삭제** 처럼 되돌릴 수 없는 동작 | **담당자** (+ 포털 관리자) |

부서 전체가 리포트를 볼 수 있어도, 남이 올린 파일을 지우는 건 한두 사람만
할 수 있어야 한다. 반대로 삭제를 포털 관리자만 할 수 있게 두면, 앱이 열 개가
되는 순간 IT 담당자가 모든 부서의 "이 파일 지워주세요"를 전부 받게 된다.

포털 관리자는 지정하지 않아도 항상 담당자로 본다. 담당자가 퇴사했을 때
아무도 손댈 수 없게 되는 상황을 막는다.

앱 쪽에서는 `/api/verify?service=xxx` 의 `manage` 값을 보고 판단한다.
`allowed` 는 "쓸 수 있나", `manage` 는 "관리할 수 있나"다.

### 서비스와 도구의 관계

```
[관리자 화면]  서비스 "자산관리" — 인사총무팀만
                        │
                        ├─ 좌측 앱 카드 / 앱 런처
                        ├─ find_app 안내 대상
                        └─ @tool(service="assets") 도구의 사용 권한
```

한 곳에서 접근 범위를 바꾸면 **화면과 챗이 동시에 바뀐다.**
"화면엔 안 보이는데 챗으로 물으면 답한다" 같은 사고가 구조적으로 생기지 않는다.

권한이 없는 사용자에게는

- 좌측 카드에 나타나지 않고
- AI 도 그 앱을 안내하지 않으며
- 관련 조회 도구가 목록에서 제외되고
- 도구 이름을 직접 지정해도 실행 시점에 다시 막힌다

즉 **앱의 존재 자체가 노출되지 않는다.**

> 단, 이것은 포털 쪽 방어다. 실제 방어선은 각 앱이 자체적으로 수행하는
> 권한 검사다. 포털에서 숨겼다고 앱의 검사를 제거하면 안 된다.

### 검색이 잘 되게 하려면

서비스의 `keywords` 를 충실히 채울 것. 앱 런처 검색과 `find_app` 도구가
모두 이 값을 쓴다. 직원이 실제로 쓰는 표현을 넣는다 — "노트북", "장비",
"반납" 처럼 앱 이름에 없는 말이 오히려 중요하다.

## 9-1. 관리자 화면 (/admin)

관리자로 로그인하면 사이드바에 **계정 관리** 가 나타난다. 탭 세 개로 나뉜다.

### 서비스 관리

| 기능 | 내용 |
|---|---|
| 서비스 추가·수정 | id, 이름, 주소, 설명, 검색 키워드, 색 |
| 접근 범위 설정 | 전 직원 / 부서·개인 지정 |
| 사용 토글 | 중지하면 목록과 도구에서 함께 사라진다 |
| 순서 변경 | ↑ ↓ — 포털 화면의 카드 순서 |
| 삭제 | 연결된 챗 도구도 함께 잠긴다 |

접근 범위 창에서 부서를 체크하면 그 부서 전체가 허용된다.
오른쪽 `N명 ▾` 을 눌러 펼치면 개인별 체크가 나오고, 체크를 풀면 그 사람만 제외된다.
부서를 체크하지 않은 상태에서는 개인 목록이 잠긴다 — 권한이 있는 것처럼 보이면
잘못 설정하기 때문이다.

### 부서 관리

부서명은 접근 범위 판정의 기준이다. "인사총무팀"과 "인사총무 팀"이 섞이면
서로 다른 부서로 잡히고, 그 순간 **권한을 줬는데 안 보이는** 상태가 된다.
그래서 부서는 이 탭에 등록된 것 중에서만 고르게 되어 있다.
사용자 화면의 부서 칸도 자유 입력이 아니라 선택 목록이다.

| 기능 | 내용 |
|---|---|
| 부서 추가 | 여기 등록해야 계정에 지정할 수 있다 |
| 이름 변경 | 계정의 소속과 서비스 접근 범위에 적힌 이름을 **함께** 바꾼다 |
| 순서 변경 | 목록에 나오는 순서 |
| 삭제 | 쓰고 있는 곳이 남아 있으면 막힌다 |

각 부서 옆에 소속 직원 수와 그 부서를 쓰는 서비스가 함께 표시된다.
이름을 바꾸기 전에 무엇이 같이 바뀌는지 먼저 보여 준다.

> 부서를 번호(id)로 참조하고 조인하는 방식도 있다. 여기서는 이름을 그대로
> 저장하고 대신 **입력 경로를 목록으로 좁히는** 쪽을 택했다. 이 규모에서는
> DB 를 열었을 때 `dept` 칸에 "인사총무팀"이라고 적혀 있는 편이 `dept_id=3`
> 보다 문제를 훨씬 빨리 찾게 해주고, 조인이 users·services 양쪽에 붙으면
> 접근 판정 코드가 복잡해지기 때문이다. 이름이 흩어져 따로 노는 문제는
> `depts.rename()` 이 관련 테이블을 한 번에 고쳐서 막는다.

### 사용자 명부

| 기능 | 내용 |
|---|---|
| 계정 추가 | 아이디·이름·부서·관리자 여부·초기 비밀번호 |
| 수정 | 이름·부서·관리자 여부 |
| 비밀번호 | 관리자가 초기화 후 전달 (본인이 첫 로그인 때 다시 변경) |
| 중지 / 재개 | 퇴사·복직 처리 |

부서는 **부서 관리** 탭에 등록된 것 중에서만 고를 수 있다.
찾는 부서가 없으면 거기서 먼저 등록한다.

안전장치가 걸려 있다.

- 마지막 관리자의 관리자 권한은 해제할 수 없다
- 마지막 관리자는 중지할 수 없다
- 자기 계정은 중지할 수 없다

### 이력

두 표로 **나뉘어** 있다.

| 표 | 담는 것 |
|---|---|
| 관리 이력 | 포털 설정 변경 + 각 서비스의 파일 업로드·다운로드·삭제 |
| 챗 사용 기록 | 누가 언제 어떤 기능을 썼는지 — **질문 내용은 없다** |

관리 이력은 **서비스**와 **동작**으로 걸러 볼 수 있다.
"AI 리포트에서 지난주에 누가 뭘 받아갔나" 같은 것을 두 번 클릭으로 본다.

각 앱은 `POST /api/audit` 으로 자기 동작을 보낸다. 앱마다 이력이 흩어져
있으면 사고가 났을 때 화면을 여러 개 뒤져야 한다. 한곳에 모으되
`service` 열로 구분한다.

챗 사용 기록을 따로 두는 이유는 **9-2** 참고.

## 9-2. 챗 기록

**질문과 답변을 기록한다.** 사내 도구에서는 이 기록이 곧 개선 재료다.
"직원들이 실제로 뭘 어떻게 묻는가"를 봐야

- 도구 설명(description)을 고쳐 정확도를 올리고
- 엉뚱한 도구를 부르는 경우를 잡고
- 어떤 앱을 더 만들어야 하는지 알 수 있다

### 저장되는 것

| 저장되는 것 | 어디에 | 누가 볼 수 있나 |
|---|---|---|
| 대화 내역 (전문 + 바로가기) | `turns` | **본인만.** 사이드바의 대화 내역 |
| 대화 제목 (첫 문답 한 줄 요약) | `session_titles` | **본인만.** 사이드바 목록 |
| 사용 기록 (누가·언제·도구·질문·답변) | `logs` | 관리자 |
| 관리 동작 · 각 앱의 파일 동작 | `audit` | 관리자 |

```ini
CHAT_LOG_TEXT=on     # 기본. 질문·답변까지 남긴다
CHAT_LOG_DAYS=90     # 사용 기록 보관 일수
CHAT_KEEP_DAYS=365   # 본인 대화 내역 보관 일수
CHAT_TITLES=on       # 기본. 대화 목록 제목을 한 줄로 요약해서 붙인다
```

`CHAT_TITLES` 는 첫 문답이 끝난 뒤 **별도 스레드에서** 모델을 한 번 더 불러
"6월 AI 사용량 조회" 같은 제목을 만든다. 답변이 늦어지지 않고,
실패하면 예전처럼 첫 질문이 그대로 제목이 된다. `off` 로 두면 이 호출을 안 한다.

보관 기간이 지난 기록은 서버가 뜰 때 자동으로 지워진다.

### 대신 지키는 것

1. **보관 기간을 둔다.** 몇 년 뒤까지 남겨 둘 이유가 없다 (`CHAT_LOG_DAYS`).
2. **관리자만 본다.** 이력 탭은 `admin_user` 로 막혀 있고,
   관리 이력과 챗 기록을 표 두 개로 나눠 둔다.

### 기록을 끄고 싶으면

```ini
CHAT_LOG_TEXT=off
```

누가 언제 어떤 기능을 썼는지만 남는다. 이미 쌓인 문장은 따로 지운다.

```bash
python manage.py purge-text
```

이력 탭 상단에 현재 설정이 그대로 표시된다.

## 10. 모델·공급자 바꾸기

도구 코드와 실행 루프는 그대로 두고 **`.env` 만 바꾸면** 모델을 교체할 수 있다.

### 사내 게이트웨이 (비즈라우터 등)

키 하나로 여러 모델을 쓰는 게이트웨이는 대부분 **OpenAI 호환**이다.
`PROVIDER=openai` 로 두고 주소만 게이트웨이로 돌리면 된다.

```ini
PROVIDER=openai
OPENAI_API_KEY=발급받은_게이트웨이_키
OPENAI_BASE_URL=https://<게이트웨이주소>/v1
MODEL=gpt-5-nano
```

모델명은 게이트웨이에 등록된 이름을 그대로 쓴다 (`gpt-5-nano`, `sonnet5` 등).
정확한 이름은 아래 점검 스크립트가 목록으로 보여준다.

### Anthropic 직접 사용

```ini
PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
MODEL=claude-opus-5
```

### 연결 점검 — 서버 띄우기 전에

```bash
python check_llm.py
```

네 가지를 순서대로 확인한다.

1. 설정값 (공급자·모델·주소·키)
2. 게이트웨이가 제공하는 **모델 목록** — 설정한 이름이 실제로 있는지 대조
3. 일반 대화가 되는지
4. **도구 호출이 되는지** ← 가장 중요

4번이 실패하면 그 모델로는 이 포털을 만들 수 없다. 다른 모델로 바꿔 다시 시험한다.

### 모델 선택 요령

| 용도 | 권장 |
|---|---|
| 개발·시험 | 가장 저렴한 모델. 도구 호출만 되면 충분 |
| 실제 운영 | 중간 등급 이상. 라우팅 정확도 차이가 크다 |

작은 모델은 **도구를 고르는 판단이 약할 수 있다.** 도구가 5~10개까지는 대체로 무난하지만,
개수가 늘거나 비슷한 기능이 많아지면 오답이 는다.

개발은 저렴한 모델로 하고, 도구가 어느 정도 갖춰진 뒤
**같은 질문 20개 정도로 모델별 정확도를 비교**해 보고 운영 모델을 정하는 방식을 권한다.
`/api/logs` 에 쌓인 실제 질문을 그 시험 문항으로 쓰면 된다.

> `.env` 만 바꿔 재시작하면 되므로 비교는 몇 분이면 끝난다.

## 11. 화면과 응답 속도

### 진행 표시 (SSE)

`/api/chat/stream` 은 처리 단계를 실시간으로 흘려보낸다.

```
생각하는 중  →  ✓ 사내 앱 검색  →  답변 정리하는 중  →  최종 답변
```

토큰 단위 스트리밍은 아니지만, **무엇을 하는 중인지 보이면 체감 속도가 크게 달라진다.**
`/api/chat` 은 한 번에 받는 기존 방식으로 그대로 남겨 두었다.

진행 표시에 쓰는 한글 이름은 도구 정의의 `label` 로 지정한다.

```python
@tool(
    name="get_ai_cost",
    label="AI 사용비용 조회",      # 화면에 이렇게 표시됨
    description="...",
)
```

`label` 을 생략하면 도구 이름이 그대로 나온다.

### 응답이 느린 이유

도구를 쓰는 질문은 모델을 **두 번** 부른다. 구조상 줄일 수 없다.

| 단계 | 소요 |
|---|---|
| 1차 호출 — 어느 도구를 부를지 판단 | 1~3초 |
| 도구 실행 — 우리 서버 | 대개 0.1초 미만 |
| 2차 호출 — 결과를 문장으로 정리 | 1~3초 |

줄일 수 있는 것은 다음 정도다.

- `MAX_TOKENS` 를 낮춘다 (기본 1024 → 512)
- 도구가 돌려주는 `data` 를 줄인다. 목록 전체를 넘기지 말고 요약과 링크만
- 더 빠른 모델을 쓴다
- 도구가 필요 없는 인사말 등은 1회 호출로 끝나므로 이미 빠르다

### 화면 손보기

`static/chat.html` 한 파일이다. 자주 고칠 만한 곳:

| 항목 | 위치 |
|---|---|
| 색상·다크모드 | 최상단 `:root` / `prefers-color-scheme` |
| 예시 질문 칩 | `const CHIPS = [...]` |
| 로고·포털명 | `<aside>` 의 `.brand` |
| 최대 폭 | `.wrap`, `.composer` 의 `max-width` |

## 12. 답을 못 할 때 (도구 반복 호출)

화면에 도구 호출만 여러 개 찍히고 답이 안 나오는 경우가 있다.
모델이 결과를 받고도 판단을 못 해 같은 조회를 반복하다 상한에 걸린 것이다.

### 진단

```bash
python debug_chat.py "이번달 ai 사용량 알려줘"
```

도구가 **실제로 무엇을 돌려줬는지** 한 줄씩 보여준다.

| 관찰 | 원인 | 조치 |
|---|---|---|
| `→` 줄에 값이 정상 표시됨 | 모델의 판단 문제 | 더 큰 모델로 교체 (`MODEL` 변경) |
| `→` 줄에 오류 메시지 | 도구 문제 | 엑셀 경로·열 이름 확인 |
| 도구가 아예 안 불림 | 설명 문제 | `description` 에 사용자 표현 추가 |

### 이미 적용된 방지 장치

- **반복 호출 차단** — 같은 도구를 같은 값으로 다시 부르면 재실행하지 않고
  이전 결과를 돌려주며 "이 결과로 답하라"고 알린다.
- **반복만 하면 중단** — 한 라운드가 전부 중복이면 루프를 빠져나온다.
- **최종 답변 강제** — 상한에 도달하면 도구를 뺀 채 한 번 더 호출한다.
  도구를 못 쓰면 모델은 지금까지 받은 결과로 답할 수밖에 없다.

### 그래도 반복하면

작은 모델일수록 비슷한 도구를 구분하지 못한다. 순서대로 시도한다.

1. 겹치는 도구의 `description` 에 구분 기준을 명시
   - `get_ai_cost` → "합계 금액만 필요할 때. 목록이 필요하면 list_ai_usage"
   - `list_ai_usage` → "개별 내역이 필요할 때. 합계만이면 get_ai_cost"
2. `MODEL` 을 한 단계 올려 비교 (`gpt-5-mini`, `anthropic/claude-sonnet-5`)
3. 도구 수를 줄이거나 하나로 합친다

## 13. 대화 내역과 앱 런처

### 배치 원칙

| 위치 | 담는 것 | 이유 |
|---|---|---|
| 사이드바 | **대화 내역** | 자주 오가는 것. Claude·ChatGPT 와 같은 위치라 학습 비용이 없다 |
| 상단 우측 `앱` 버튼 | **앱 목록 (검색 포함)** | 가끔 쓰는 것. 개수가 늘어도 화면을 잠식하지 않는다 |
| 첫 화면 | 예시 질문 + 앱 카드 6개 | 처음 온 사람에게만 보여주면 충분하다 |

앱을 사이드바에 상시 나열하지 않는 이유가 하나 더 있다.
**이 포털의 목적이 "앱을 찾아주는 것"인데 목록을 늘어놓으면 원래 문제로 되돌아간다.**
앱이 늘어날수록 목록은 더 안 보이게 하고, 검색과 채팅으로 찾게 하는 것이 맞다.

플로팅 버튼은 대화 내용을 가리고 좁은 화면에서 입력창과 겹치므로 쓰지 않았다.

### 바로가기 버튼은 대화와 함께 저장된다

`turns` 테이블에 `links` 열을 둔다. 답변 텍스트만 저장하면 나중에 그 대화를
다시 열었을 때 버튼이 사라진다. 답에는 "리포트 화면에서 확인하세요"라고
적혀 있는데 정작 갈 버튼이 없으면, 답이 잘못된 것처럼 보인다.

### 대화 내역 API

| 엔드포인트 | 용도 |
|---|---|
| `GET /api/sessions` | 목록. 제목은 그 대화의 첫 질문에서 자동 생성 |
| `GET /api/sessions/{id}` | 대화 전문 |
| `DELETE /api/sessions/{id}` | 삭제 |

**본인 대화만 조회된다.** 조회·삭제 모두 `user_id` 를 함께 대조하므로
남의 `session_id` 를 알아내도 열리지 않는다.

### 앱이 많아지면

첫 화면의 앱 카드는 **최대 6개**까지만 깔린다. 넘어가면
`자주 쓰는 앱 · 전체 N개` 로 표시하고 아래에 `앱 N개 모두 보기` 버튼이 붙어
앱 런처(검색 가능)를 연다. 개수 상한은 `static/chat.html` 의 `HERO_APPS`.

앱을 전부 늘어놓지 않는 이유는 화면이 좁아서만이 아니다.
100개를 다 보여주면 첫 화면이 앱 목록 페이지가 되고, 정작 챗 입력창이
아래로 밀린다. **이 포털은 앱을 찾아주는 것이 목적인데 목록을 늘어놓으면
원래 문제로 되돌아간다.**

검색이 잘 되게 하려면 관리자 화면에서 각 서비스의 `keywords` 를 충실히 채울 것.
런처 검색과 `find_app` 도구가 모두 이 값을 쓴다.

```
자산, 노트북, PC, 라이선스, IP, 렌탈, 장비, 지급, 반납
```

수십 개가 되면 `category` 필드를 추가해 런처를 분류별로 묶는 것을 검토한다.

### 화면에 안 보이는 것

- **모델명과 도구 함수명은 관리자에게만 표시된다.** 일반 직원에게는
  `openai/gpt-5-mini` 나 `get_ai_usage` 가 아무 의미가 없고, 진행 중에 이미
  한글 이름("AI 사용 현황 조회")으로 보여줬으므로 중복이다.
  문제를 추적할 때는 관리자 계정으로 같은 질문을 해보면 된다.
- 사이드바의 계정 아래에는 **소속 부서**가 표시된다. 관리자면 `부서 · 관리자`.
  권한 이름을 나열하던 자리인데, 직원이 알 필요도 없고 알아도 쓸 데가 없다.

## 14. 도구는 적을수록 좋다

비슷한 도구가 둘이면 모델이 **"요약을 원하세요, 목록을 원하세요?"** 하고 되묻는다.
사용자 입장에서는 한 번에 답이 안 나오는 것이라 사용성이 나빠진다.

그래서 `get_ai_cost` 와 `list_ai_usage` 를 `get_ai_usage` 하나로 합쳤다.

```
합계 + 서비스별 비중 + 사용자별 비중 + 최근 내역 5건 + 상세 링크
```

한 번의 조회로 "얼마야"와 "내역 보여줘"를 모두 답할 수 있다.
건수가 많으면 `truncated` 로 표시해 링크 안내로 넘어간다.

### 되묻기 억제

시스템 프롬프트에 다음을 넣어 두었다.

- 기본값으로 진행할 수 있으면 되묻지 않는다 (월 미지정 → 이번 달)
- 조회 대상이 정말 특정되지 않을 때만 되묻는다
- 한 번에 답할 수 있으면 도구를 여러 번 부르지 않는다

### 도구를 나눠야 할 때

- **동작이 다를 때** — 조회와 등록·수정은 반드시 분리한다
- **권한이 다를 때** — 전 직원용과 관리자용
- **응답 크기가 크게 다를 때** — 요약과 원본 전체 내려받기

단지 "출력 형태가 다르다"는 이유로는 나누지 않는다. 그건 한 도구의 옵션으로 처리한다.

## 15. 로그인과 계정

포털 자체 계정 체계. **회원가입 화면은 없다.** 관리자가 계정을 만든다.
사내 시스템에 셀프 가입을 열면 아무나 사내 데이터에 접근하게 된다.

### 준비

`.env` 에 서명키를 넣는다. 유출되면 누구나 로그인할 수 있으므로 반드시 바꿀 것.

```bash
python -c "import secrets;print(secrets.token_urlsafe(48))"
```

```ini
JWT_SECRET=위에서_생성한_문자열
JWT_EXPIRE_HOURS=12
USER_DB=./data/users.db
```

### 최초 관리자 만들기 — 서버에서 1회

**웹에서는 첫 관리자를 만들 수 없다.** 만들 수 있게 하면 서버를 띄운 직후
누구든 먼저 접속해서 관리자가 되는 구멍이 생긴다. 서버 접근 권한이 있는
사람만 할 수 있도록 CLI 로 남겨 두었다.

```bash
python manage.py add admin "관리자" --dept "인사총무팀" --admin --password "Abcd123!"
```

`--password` 를 생략하면 입력을 받고, 그냥 Enter 를 치면 자동으로 만들어 준다.

> 일부 윈도우 터미널에서 비밀번호 입력이 `KeyboardInterrupt` 로 끊기는 경우가 있다.
> 그때는 `--password` 로 바로 지정하면 된다.

이후로는 이 계정으로 로그인해 **웹 `/admin` 에서** 나머지 계정을 만든다.

### 웹 계정 관리 — /admin

두 번째 계정부터는 웹에서 만든다. 화면 구성은 **9-1** 항목 참고.

### CLI 명령 (서버에서)

웹에 들어갈 수 없을 때를 위한 최소한의 수단이다. 평소에는 웹을 쓴다.

| 명령 | 용도 |
|---|---|
| `add <id> <이름> --dept 부서 [--admin]` | 계정 생성 |
| `list` | 목록 (부서·구분·상태·최근 로그인) |
| `passwd <id>` | 비밀번호 초기화 |
| `dept <id> <부서>` | 부서 변경 (등록된 부서만) |
| `depts` / `depts --add <부서>` | 부서 목록 / 부서 추가 |
| `admin <id> on\|off` | 관리자 권한 부여·회수 |
| `off <id>` / `on <id>` | 사용 중지 / 재개 |
| `purge-text` | 쌓인 질문·답변 원문 삭제 |
| `titles` | 제목 없는 지난 대화에 제목 붙이기 (`--dry-run` 으로 미리보기) |

**퇴사자는 `off` 로 처리한다.** 계정을 지우면 대화 기록의 소유자를 알 수 없게 된다.

### 권한 구분

| 구분 | 부여되는 것 |
|---|---|
| 관리자 | `/admin` 화면, 전체 이력 열람 |
| 일반 | 소속 부서에 허용된 서비스 |

그 외 세부 권한은 역할이 아니라 **서비스별 접근 범위**로 관리한다 (9 항목).

### 동작

```
/login 에서 아이디·비밀번호 입력
   -> 서버가 확인 후 JWT 발급
   -> 브라우저가 저장하고 이후 요청에 Authorization 헤더로 첨부
   -> 만료되거나 유효하지 않으면 자동으로 /login 으로 이동
```

비밀번호는 pbkdf2(26만 회)로 해시해 저장한다. 원문은 어디에도 남지 않는다.
로그인 실패 시 "아이디가 없다"와 "비밀번호가 틀렸다"를 구분해 알려주지 않는다.

### 알아둘 점

- **권한 변경은 전부 즉시 반영된다.** 관리자 회수, 부서 변경, 계정 중지,
  서비스 접근 범위 변경 모두 다음 요청부터 적용된다. 재로그인이 필요 없다.
- 그 이유는 `app/auth.py` 의 `current_user` 가 **토큰이 아니라 DB 를 기준으로**
  삼기 때문이다. JWT 안의 값만 믿으면 관리자 권한을 회수해도 토큰이 만료되는
  12시간 동안 관리자 API 가 그대로 열려 있다. 화면에서 메뉴가 안 사라지는
  정도가 아니라 **구멍**이므로, 요청당 SQLite 조회 한 번을 감수하는 쪽이 맞다.
- 토큰은 "이 사람이 누구인지"만 증명하고, "무엇을 할 수 있는지"는 매번 DB 가 정한다.
- 사용자가 수백 명을 넘어 이 조회가 부담이 되면 짧은 캐시(수십 초)를 두면 된다.
  토큰 수명을 늘리는 방향은 아니다.
- 운영 전에 HTTPS 를 적용할 것. 비밀번호와 JWT 가 평문으로 오간다.

## 16. 초기 비밀번호와 첫 로그인

**초기 비밀번호는 쉬운 것으로 줘도 된다.** 첫 로그인 때 본인이 반드시 바꾸게 되므로
오래 남지 않는다. `Abcd123!` 같은 형태로 전달하면 전화로 불러주기도 쉽다.

```
관리자가 계정 생성 (초기 비밀번호 전달)
   -> 본인이 첫 로그인
   -> 비밀번호 변경 화면으로 자동 이동 (건너뛸 수 없음)
   -> 변경하면 포털로 진입
```

| 상황 | 이후 상태 |
|---|---|
| 관리자가 계정 생성 | 변경 필요 |
| 관리자가 비밀번호 초기화 | 변경 필요 |
| 본인이 직접 변경 | 정상 |

계정 목록에서 아직 안 바꾼 사람은 **비번 변경 필요** 로 표시된다.

### 본인 비밀번호 변경

사이드바의 **비밀번호 변경** 으로 언제든 바꿀 수 있다. 현재 비밀번호를 반드시 확인한다.

- 8자 이상
- 이전과 같은 비밀번호는 거부
- 변경하면 새 토큰이 발급되어 변경 필요 표시가 사라진다

### 초기 비밀번호 자동 생성

계정 추가 화면의 **자동** 버튼을 누르면 `Green2416!` 형태로 만들어 준다.
읽어주기 쉬우면서 추측하기 어려운 형태다.
CLI 에서도 비밀번호 입력 시 그냥 Enter 를 치면 같은 방식으로 생성된다.

## 17. 서버 배치 구조

기존 서버 방식을 그대로 따른다. **서비스마다 폴더를 나란히 둔다.**

```
/srv/portal/
├── portal/          ← 챗 포털 (메인). 이 레포
│   ├── app/ static/ Dockerfile docker-compose.yml
│   ├── .env         ← 서버에만. git 에 올리지 않는다
│   └── data/        ← SQLite 3개. 백업 대상
├── ai-report/       ← 별도 레포
│   ├── main.py index.html Dockerfile docker-compose.yml
│   └── data/        ← 월별 엑셀. 백업 대상
├── assets/
└── proxy/           ← nginx. 하나의 주소로 묶는다
```

### 포털 안에 넣지 않는 이유

팀에서 각자 레포를 만들어 커밋하고 검토 후 배포하는 방식이라
**서비스 하나가 곧 레포 하나**다. 포털 안에 ai-report 를 넣으면
두 사람이 같은 레포를 건드리게 되고, 포털만 고쳐도 ai-report 가 함께 재배포된다.

compose 도 합치지 않는다. 하나로 묶으면 `docker compose up -d --build` 한 번에
전부 재시작된다. 서비스가 넷을 넘어가면 "매뉴얼 오타 하나 고쳤는데 챗이 끊겼다"가 생긴다.

대신 **같은 도커 네트워크**에 붙여 서로 컨테이너 이름으로 부른다.

```bash
docker network create demo-net      # 처음 한 번만
```

### 주소

nginx 하나가 앞에 서고 뒤로 넘긴다. 직원은 포트 번호를 몰라도 된다.

| 주소 | 가는 곳 |
|---|---|
| `/` | portal:8080 |
| `/ai-report/` | aireport:8080 |
| `/assets/` | assets:8080 |

관리자 화면에서 서비스를 등록할 때 **경로(URL)** 칸에 `/ai-report/` 를 넣으면
이 체계와 그대로 맞는다.

### 배포

```bash
cd /srv/portal/portal
git pull && docker compose up -d --build
```

`deploy/deploy.sh` 를 `/srv/portal/` 에 두면 한 줄이 된다.

```bash
./deploy.sh portal        # 하나만
./deploy.sh               # 전부 (proxy 는 맨 마지막)
```

## 18. 서비스 사이 인증

옆 서비스도 "이 사람이 누구인지"를 알아야 한다.
**포털이 판정하고 옆 서비스는 물어보기만 한다.**
판정 기준이 두 벌이 되면 "포털에선 되는데 리포트에선 안 된다"가 생긴다.

### 앱은 헤더만 읽으면 된다

nginx 가 앱 요청 앞에서 포털에 물어보고(`auth_request`), 돌아온 사용자
정보를 헤더로 붙여 준다. 앱에는 포털 관련 코드가 한 줄도 필요 없다.

```
직원 브라우저
   │  로그인 → 포털이 쿠키를 심는다
   ↓
 nginx  ──(1)── /api/authz?service=assets ──→ 포털
        ←────── 204 + X-User-Id / Name / Dept / Role
        ──(2)── 그 헤더를 붙여서 ───────────→ assets 앱
```

| 헤더 | 값 |
|---|---|
| `X-User-Id` | 아이디 |
| `X-User-Name` | 이름 (한글이라 퍼센트 인코딩) |
| `X-User-Dept` | 부서 (한글이라 퍼센트 인코딩) |
| `X-User-Role` | `admin` (포털 관리자 또는 그 서비스의 담당자) / `user` |

- 권한이 없으면 요청이 **앱에 도달조차 하지 않는다** (403 화면).
- 직원이 `X-User-Role: admin` 을 직접 붙여 보내도 nginx 가 덮어쓴다.
- 접근 범위를 관리자 화면에서 바꾸면 모든 앱에 즉시 반영된다.

### 앱 하나에 설정 파일 하나

프록시 설정은 두 층으로 나눠 둔다.

```
proxy/
  conf.d/portal.conf     공통. 포털(/), 401·403 화면, apps/ 를 include
  apps/ai-report.conf    ai-report 전용 두 블록
  apps/meeting-room.conf 앱이 늘면 파일이 는다
  apps/_TEMPLATE.conf.txt 본보기 (.conf 가 아니라 읽히지 않는다)
  new-app.ps1            본보기를 채워서 apps\서비스ID.conf 를 만든다
```

`portal.conf` 안에서 `include /etc/nginx/apps/*.conf;` 한 줄이 앱 파일들을
끌어온다. `location` 은 `server` 블록 안에 있어야 하므로 앱 파일에는
`server {` 를 쓰지 않고 `location` 부터 바로 적는다.

한 파일에 다 몰아넣어도 nginx 는 동작한다. 나누는 이유는 사람 쪽이다.

| | 한 파일에 다 | 앱마다 한 파일 |
|---|---|---|
| 앱 추가 | 공용 파일을 연다 (다른 앱 설정 옆에서 편집) | 파일 하나 넣는다 |
| 앱 제거 | 어디부터 어디까지인지 찾아서 지운다 | 파일 하나 지운다 |
| 오타가 났을 때 | 어느 앱 때문인지 안 보인다 | 파일 이름이 곧 범인 |
| 되돌리기 | 공용 파일 되돌리면 다른 앱도 같이 | 그 파일만 |

새 앱을 붙일 때는 이 한 줄이면 된다.

```powershell
.\new-app.ps1 meeting-room        # apps\meeting-room.conf 생성
.\deploy.ps1 proxy                # 설정 다시 읽기
```

컨테이너 이름이 서비스 ID 와 다르면 `-Container` 로 알려준다
(`ai-report` → `aireport` 처럼). 기본값은 하이픈을 뺀 이름이다.

### 쿠키가 필요한 이유

챗 화면은 SPA 라 토큰을 헤더에 담아 보내면 된다. 하지만 직원이 `/ai-report/`
를 누르면 그건 **다른 서버가 처리하는 일반 페이지 이동**이라 헤더를 붙일 수 없다.
그래서 로그인할 때 같은 JWT 를 쿠키로도 심는다.

```
로그인 → 포털이 portal_token 쿠키를 심는다 (HttpOnly, path=/, SameSite=Lax)
   │
   ├─→ /            챗 화면 — 헤더로 보냄
   └─→ /ai-report/  ai-report 컨테이너
                      │  브라우저가 쿠키를 자동으로 보냄
                      └─→ http://demo-portal:8080/api/me  ← 포털이 판정
```

`HttpOnly` 라 자바스크립트가 못 읽는다. XSS 로 토큰이 새 나가는 경로를 막는다.
로그아웃하면 `/api/logout` 이 쿠키까지 지운다. 이걸 빠뜨리면
**챗에서는 로그아웃됐는데 리포트는 계속 열리는** 상태가 된다.

### 옆 서비스가 쓰는 엔드포인트

| 엔드포인트 | 용도 |
|---|---|
| `GET /api/me` | 쿠키로 누구인지 확인. `logged_in`, `is_admin`, `id`, `dept` 포함 |
| `GET /api/verify?service=ai-report` | 이 사람이 그 서비스를 쓸 수 있는지 (`allowed`) |
| `POST /api/audit` | 옆 서비스의 동작을 포털 이력에 남긴다 |
| `POST /api/services/register` | 앱이 뜰 때 자기를 등록한다 (중지 상태로 들어온다) |
| `GET /api/authz?service=x` | **nginx 전용.** 통과하면 204 + 사용자 헤더 |

`/api/me` 는 기존 포털이 쓰던 이름을 그대로 유지한다. 그래서 ai-report 는
코드를 고칠 필요가 없고 `docker-compose.yml` 한 곳만 바꾸면 붙는다.

```yaml
environment:
  # IP 대신 컨테이너 이름. IP 를 박아두면 서버를 옮길 때 전부 고쳐야 한다.
  - PORTAL_API_URL=http://demo-portal:8080
  - AUDIT_TOKEN=포털_.env_의_AUDIT_TOKEN_과_같은_값
```

`/api/audit` 은 사용자 쿠키가 아니라 **서비스 사이 공유 토큰**으로 확인한다.
사람이 아니라 서버가 부르는 자리이기 때문이다. `AUDIT_TOKEN` 을 비워 두면
아예 받지 않는다 — 열어두면 사내망 안에서 누구나 이력을 지어낼 수 있다.

### /api/verify 를 쓰면

접근 범위를 관리자 화면에서 바꾸는 것만으로 옆 서비스의 접근도 같이 바뀐다.
서비스마다 명단을 또 관리하지 않아도 된다. 새 서비스를 만들 때 이걸 쓸 것.

## 19. 앱을 챗에 붙이는 방법

### 흐름

```
직원이 웹앱을 만든다
   → 검토하고 배포한다                     (서비스 폴더 + docker compose)
   → 관리자 화면에서 서비스로 등록한다      (이름·주소·키워드·접근 범위)
   → 그 앱을 부르는 도구 파일 하나를 만든다  (app/tools/xxx.py)
   → 직원이 챗으로 묻는다
   → 짧으면 답하고, 길면 요약 + 바로가기
```

### 포털은 앱의 데이터를 직접 읽지 않는다

**앱에게 물어보고 답을 옮긴다.**

```
[ai-report 컨테이너]   ← 엑셀·계산·화면을 전부 책임진다
        ↑ HTTP
[포털 컨테이너]        ← 물어보고, 줄여서 전달
```

처음에는 포털이 같은 엑셀을 열어 직접 합계를 냈다. 그러면 **같은 계산이
두 벌**이 된다. 실제로 그렇게 짜 놓고 보니 대시보드 화면은 259만 원,
챗은 165만 원을 말하고 있었다. 어느 쪽이 맞는지 확인하는 데만도 시간이
걸리고, 이런 어긋남은 눈에 잘 띄지도 않는다.

앱이 자기 숫자를 책임지고 포털은 전달만 하면 이 문제가 생기지 않는다.
그리고 앱이 늘어날 때 포털이 각 앱의 파일 형식을 알 필요가 없다.
**새 앱을 붙이는 일이 "도구 파일 하나 추가"로 끝난다.**

| | 포털이 파일을 읽는 방식 | 앱에 물어보는 방식 (지금) |
|---|---|---|
| 계산 | 두 벌 | 한 벌 |
| 새 앱 추가 | 포털이 그 앱의 데이터 구조를 알아야 함 | API 하나 부르면 끝 |
| 앱이 죽으면 | 답은 나오지만 최신인지 알 수 없음 | "연결하지 못했습니다"로 분명히 알림 |
| 앱에 DB 가 생기면 | 포털도 그 DB 를 알아야 함 | 바뀔 것 없음 |

### 엑셀이 없으면 답을 못 하나

**그건 데이터가 없는 것이지 챗의 문제가 아니다.** 대시보드도 같은 상황에서
빈 화면을 보여준다. 다만 상황을 구분해서 알린다.

| 상황 | 답 |
|---|---|
| 앱이 내려가 있음 | "AI 리포트 서비스에 연결하지 못했습니다" |
| 그 달 자료만 없음 | "2026-01 자료가 없습니다. 올라와 있는 달은 …" |
| 이번 달만 아직 없음 | 가장 최근 달로 답한다 |

마지막이 중요하다. 8월 3일에 "이번 달 사용량"을 물으면 자료가 없는 게
당연하다. "없습니다"보다 "7월 기준입니다"가 쓸모 있다.

### 답을 얼마나 줄일지는 도구가 정한다

모델에게 "10위까지만 말해" 같은 지시를 넣지 않는다. 모델은 지시를 지킬 때도
있고 안 지킬 때도 있어서 답 길이가 들쭉날쭉해진다.
**무엇을 짧은 답으로 볼지는 도구가 정해서 넘긴다.**

```python
return ToolResult(
    summary="2026-07 사내 AI 사용비용은 2,587,958원입니다. "
            "총 호출 6,275회, 사용 인원 50명입니다. "
            "많이 쓴 순으로 오채성 191,376원, 한윤현 170,204원 … 입니다. "
            "전체 48명의 순위는 리포트 화면에서 확인하세요.",
    data={...},                    # 모델이 추가 가공할 원본
    detail_url="/ai-report/?month=2026-07",   # 바로가기 버튼이 된다
    truncated=True,                # "다 못 담았다"는 신호
)
```

- `summary` — 모델은 이걸 거의 그대로 옮긴다
- `detail_url` — 화면에 **바로가기** 버튼으로 나온다
- `truncated=True` — 모델이 "자세한 건 화면에서" 라고 안내하게 만든다

### 주소는 모델에게 주지 않는다

`detail_url` 은 서버가 들고 있다가 버튼으로만 그린다. 모델에게 건네는
payload 에서는 빠지고 `has_detail_page: true` 만 남는다 (`ToolResult.for_model()`).

그대로 주면 모델이 답변 본문에 이렇게 적는다.

```
IT 매뉴얼 — SAP/M365 등 사용법 확인 (/manual/)
2026년 7월 AI 사용비용은 … https://portal.mir.example.com/ai-report?month=2026-07
```

직원 대부분은 그 경로로 무엇을 해야 하는지 모르고, 오히려 **답이 잘못
나온 것처럼 보인다.** 이동은 화면이 담당하면 된다.

프롬프트에 "주소를 쓰지 마"라고 적어 두기만 하면 지킬 때도 있고 안 지킬
때도 있다. 아예 주지 않는 편이 확실하다. 같은 이유로 `find_app` 도
앱 목록에서 `url` 을 빼고 이름과 설명만 돌려준다.

그리고 이 링크는 **접근 권한이 있는 사람에게만 간다.** 권한이 없으면
도구 자체가 목록에 없으므로 앱의 존재도 노출되지 않는다 (9 항목).

### 새 앱 붙이기 — 실제 순서

1. 앱에 조회용 API 를 하나 둔다. 화면이 쓰는 것과 **같은 계산**이어야 한다.
2. 앱이 뜰 때 포털에 자기를 등록하게 한다 (아래 참고). 관리자 화면에서
   직접 추가해도 되지만, 앱이 스스로 알리는 편이 낫다.
3. `app/tools/assets.py` 를 만들고 `@tool(service="assets")` 로 그 API 를 부른다.
4. `app/main.py` 의 import 에 추가.
5. 관리자 화면에서 **접근 범위와 담당자를 정하고 켠다.**

권한·화면 노출·이력은 서비스 등록만으로 따라온다.

### 앱이 자기를 등록한다

앱을 만든 사람이 그 앱의 이름·설명·검색 키워드를 가장 잘 안다. 그걸 IT
담당자가 관리자 화면에 옮겨 적게 하면 앱이 늘 때마다 같은 일을 반복하게 되고,
앱을 고쳐도 포털 쪽 설명은 옛날 그대로 남는다.

```python
# 앱의 main.py
@app.on_event("startup")
def register_with_portal():
    urllib.request.urlopen(urllib.request.Request(
        PORTAL_API_URL + "/api/services/register",
        data=json.dumps({
            "id": "assets", "name": "자산관리",
            "description": "직원별 자산·라이선스 지급 현황",
            "keywords": "자산, 노트북, PC, 라이선스, IP, 렌탈, 반납",
            "url": "/assets/",
        }).encode(),
        headers={"Content-Type": "application/json",
                 "X-Service-Token": AUDIT_TOKEN},
        method="POST"), timeout=5)
```

**등록과 공개는 다르다.** 처음 등록되는 서비스는 항상 이렇게 들어온다.

```
enabled = False        중지 상태
access  = restricted   허용 부서·개인 없음 → 아무에게도 안 보인다
```

앱이 스스로 켤 수는 없다. 관리자 화면에 **설정 필요** 로 표시되고,
접근 범위를 정하고 켜야 직원에게 보인다. 검토하고 배포하는 흐름은 그대로다.

이미 있는 서비스면 **설명 항목만** 갱신한다. 접근 범위·담당자·사용 여부는
건드리지 않는다. 앱을 재배포했다고 관리자가 정한 권한이 되돌아가면 사고다.

## 20. ai-report 연결 상세

```ini
# .env
AI_REPORT_API=http://demo-aireport:8080   # 도커: 컨테이너 이름
AI_REPORT_URL=/ai-report/            # 직원이 눌러서 갈 주소
AI_REPORT_TIMEOUT=5                  # 앱이 죽어도 챗이 멈추지 않게
```

**ai-report 쪽은 고칠 것이 없다.** 이미 있는 엔드포인트를 쓴다.

| 부르는 것 | 쓰는 값 |
|---|---|
| `GET /api/files` | 올라와 있는 달 목록 (`2026_07.xlsx` → `2026-07`) |
| `GET /api/data/{filename}` | `overview`(총액·호출·인원) + `userSummary`(사용자별) |

`__system__` 로 시작하는 계정(감사로그·IP허용 등 부가서비스)은 사람이 아니므로
순위에서 뺀다. 리포트 화면도 같은 기준으로 처리한다.

> 화면의 총액과 챗의 총액이 다르게 보이면, 두 곳이 **다른 파일**을 보고 있는
> 것이다. 리포트 화면에서 어떤 파일이 선택돼 있는지 먼저 확인할 것.
